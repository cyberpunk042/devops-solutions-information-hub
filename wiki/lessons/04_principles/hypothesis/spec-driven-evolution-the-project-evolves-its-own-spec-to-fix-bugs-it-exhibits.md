# Lesson — Spec-driven evolution: the project evolves its own spec to fix bugs

## Summary

A spec-driven project's spec is not a static description of what the project IS. It's a LIVING artifact that EVOLVES when bugs are exhibited. The structural answer to a bug is: update the spec (rules, hooks, brain files, methodology config, code) so the bug doesn't recur. The project gets BETTER over time because the spec ABSORBS the learnings.

Per operator's canonical statement (2026-05-05, verbatim): *"WE WILL FUCKING EVOLVE TO FIX IT... THIS IS THE WHOLE POINT OF EVERYTHING."*

This is the meta-doctrine that frames every other discipline:
- Bug-fix flow (log → analyze → identify → fix → verify → confirm) — the MECHANICS of evolution
- Operating principles — the RULES that the spec-evolution must respect
- Modes / autopilot loops — the WORK CADENCE for evolution
- Co-evolution between project and second-brain — evolution at the ECOSYSTEM level

All of these are operationalizations of "evolve the spec to fix bugs." None is the doctrine itself.

## Context

This principle applies when:
- A spec-driven project exists (repo carries the spec; install.sh + brain files + wiki ARE the spec)
- Bugs, anti-patterns, or recurring failures are observed
- The project has multiple layers (rules, hooks, brain files, methodology config, code) where fixes can land
- The aspiration is for the project to get BETTER over time, not just stay functional

Does NOT apply to: projects with frozen specs (e.g., regulated environments where spec changes require external approval); one-shot scripts with no future-evolution surface.

## The discipline (operator-named)

Operator's verbatim sequence: *"WHAT DOES IT LEAD TO ? A LOG... THE COME AFTER ? AN ANALYSIS ? and so on... it shoul dbe natural for you to identify those require to fix what we consider brain files and project files to solve the issue by following the required patterns and in order."*

The spec-evolution flow:
1. **Log** the bug (verbatim primary source — sacrosanct)
2. **Analysis** (root cause)
3. **Identify** spec elements (brain files, rules, hooks, etc.) that must change to embed the fix
4. **Fix in order** (deepest layer first)
5. **Verify** (confirm fix held; no regressions)
6. **Confirm** with operator (per workblock-priority rule)

This is the MECHANICAL flow. It should be NATURAL for the agent to follow it; if it's not natural, the agent itself has a bug to fix structurally (meta-evolution).

## Anti-patterns observed (when evolution doesn't happen)

| Anti-pattern | Why bad |
|---|---|
| **Verbal acknowledgment without spec change** | The bug stays in the spec; recurs |
| **One-off fix without rule** | Agent fixes the immediate symptom but not the structural cause; bug returns |
| **Fix in agent memory only** (no file change) | Agent forgets after compaction or session end; bug returns |
| **Promise to "be more careful"** | Promises don't compile; rules do |
| **Skip the analysis step** | Fix the symptom, miss the cause; recurrence likely |
| **Stop at analysis** | Understand the cause, don't apply the fix; bug not addressed structurally |
| **Confirm self-completion** | Without operator verification, the fix may not have actually worked |

Each anti-pattern blocks evolution. The discipline (mechanical flow) is what makes evolution actually happen.

## When evolution is hard

Some bugs resist easy spec-evolution:
- **Behavioral bugs in the agent itself** — rule says "don't freeze" but agent freezes anyway. Structural fix is harder; may require hook-based enforcement, mechanical sequence, or skill changes.
- **Cross-project bugs** — fix in one project; lesson must propagate to others. Sister-project applicability is the propagation channel.
- **Emergent bugs** — bug that only appears under specific operator + agent + state combinations. Hard to reproduce; harder to trace cause.

For these, operator's *"create the model to help you see it"* applies: when stuck, AUTHOR a model. The model construction itself is the breakthrough.
